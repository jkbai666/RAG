## 1. 目标与成功标准

面向需要用自己文档进行问答的使用者，提供一个本地可运行、能验证 RAG 完整链路的小项目。

第一版完成的标志：

1. 用户可以上传一份支持的文档，看到处理结果和实际参与检索的分块。
2. 用户可以针对文档提问，系统通过检索文档分块生成回答，而不是直接调用模型自由回答。
3. 每条有知识库依据的回答都能查看对应文档和分块原文。
4. 找不到足够依据、文档处理失败或模型调用失败时，界面明确说明，不伪装成功。
5. 重启服务后，已成功导入的文档和分块仍可使用。

不以“界面能展示聊天消息”或“模型返回了文本”单独作为项目完成依据。

## 4. 使用方与核心场景

第一版只有一种使用者，不区分管理员和普通用户。

**场景一：建立知识库。** 用户进入“文档管理”，上传文件，等待处理完成，打开分块详情，确认文本已被正确提取和切分。

**场景二：基于文档找答案。** 用户进入“知识库问答”，输入问题，阅读回答，并打开来源分块核对依据。

**场景三：移除错误资料。** 用户在文档管理中删除文档；删除成功后，新问题不再检索到该文档。

## 7. 页面、链路与数据设计

### 7.1 两个独立前端

问答端和文档管理端分别有独立访问地址，不设置共享应用壳或公共登录入口。双方可提供指向另一前端的普通链接，目标地址通过配置提供，默认在新标签页打开。界面采用简体中文。

**前端一：知识库问答端**

```text
┌──────────────────────────────────────────────┐
│ 知识库问答                   [打开文档管理]   │
├──────────────────────────────────────────────┤
│                                              │
│   用户问题                                   │
│   助手回答                                   │
│   来源：[文档 A · 分块 3] [文档 B · 分块 1]   │
│                                              │
│   [输入问题……]                      [发送]   │
└──────────────────────────────────────────────┘
```

- 采用常见 AI 问答的消息列表与底部输入区，不复制完整 AI 产品功能。
- 空知识库时提示“请先导入文档”，提供文档管理入口，禁用发送。
- 当前页可累计展示多次问答，但明确提示“每次提问独立处理，不记忆上下文”。
- 等待期间显示“正在检索并生成回答”，防止重复发送；第一版不细分后台执行阶段。
- 点击来源，展开本条回答的分块原文、文件名、分块编号；PDF 有页码时同时展示页码。
- 从问答端在新标签页打开文档管理端，原问答标签页保留当前消息；刷新或关闭问答页后清空，不保存历史会话。两个前端不共享浏览器内存状态。
- 从文档管理端返回原问答标签页时，重新查询知识库是否有就绪文档；导入或删除的结果由共享后端读取，不要求 WebSocket 或跨应用实时消息同步。

**前端二：文档管理端**

```text
┌──────────────────────────────────────────────┐
│ 文档管理                     [打开知识库问答] │
├──────────────────────────────────────────────┤
│ [选择文件并导入]   TXT / MD / 文本型 PDF      │
├───────────────────────┬──────────────────────┤
│ 文档列表              │ 所选文档的分块       │
│ 文件名 / 状态 / 块数  │ 分块 1：正文……      │
│ [查看分块] [删除]     │ 分块 2：正文……      │
│                       │ ……                   │
└───────────────────────┴──────────────────────┘
```

- 支持文件选择上传，不要求拖拽上传或上传前预览。
- 列表默认按导入时间倒序；显示完整文件名的可访问方式，不要求列表筛选或搜索。
- 就绪文档可查看分块；处理中文档展示等待状态，失败文档展示失败原因。
- 分块按原文顺序排列，提供独立滚动或分页，不能仅展示截断摘要。
- 没有文档时展示上传引导，没有选择文档时提示选择文档。
- 删除前二次确认，说明将同时移除该文档的分块和检索数据。

以上线框及 v2 草案是本版 UI 设计依据，没有另附视觉设计稿。文档管理端桌面采用左右布局，窄屏可上下排列。两个前端都须支持键盘操作、可见焦点、明确的加载与错误反馈，正文不得撑出页面。

### 7.2 最小处理链路

**导入：**

文档管理端上传 → Java 后端校验与提取文本 → 自动切分 → MySQL 保存分块及来源 → LangChain4j 调用向量模型 → Chroma 写入向量索引 → MySQL 将文档标记为“就绪”。

**问答：**

问答端提交问题 → Java 后端通过 LangChain4j 生成问题向量 → Chroma 返回相关分块标识与分数 → 根据 MySQL 校验文档状态并读取分块原文 → LangChain4j 调用生成模型 → 返回回答与来源。

- 两个 Vue 前端只负责各自的输入与展示，不直接调用模型、MySQL 或 Chroma，也不互相代理业务请求。
- 一个 Java 后端提供两类前端所需的 API，负责上传校验、处理状态、LangChain4j 编排、检索、生成和来源关联。
- 本地运行时为两个前端配置后端地址；后端或开发代理允许已配置的前端来源，不默认开放所有跨域来源。
- 文档解析、向量生成、索引和问答属于同一最小后端的职责，不要求拆成微服务。
- 不引入独立任务队列；允许后端在进程内处理导入，页面查询处理结果。

### 7.3 最小数据要求

下表描述需要保留的信息，不规定数据库表结构或接口字段名称。

| 对象 | 必要信息 | 保存要求 |
| --- | --- | --- |
| 文档 | 唯一标识、原文件名、格式、大小、导入时间、处理状态、失败原因、分块总数。 | MySQL 持久化，作为文档状态的权威来源。 |
| 分块 | 唯一标识、所属文档、文档内序号、分块正文、可用的 PDF 页码、向量关联信息。 | MySQL 持久化正文和来源，为分块查看及引用核验提供数据。 |
| 向量索引 | 分块向量、稳定的分块标识、文档标识及检索所需元数据。 | Chroma 持久化；与 MySQL 通过标识关联，必须来源于同一份分块。 |
| 问答结果 | 本次问题、回答、来源分块标识与原文快照。 | 仅保留在当前页面内存中。 |

原始上传文件可以在处理结束后清理，不要求原文件下载或备份功能。MySQL 和 Chroma 均需保留数据卷或持久化目录，不能只使用临时或进程内存数据。Chroma 如按集成需要同时保存分块文本，该副本必须由 MySQL 中同一分块生成，不成为第二套可独立修改的正文。失败记录可以保留，但不得作为可检索文档。

### 7.4 文档状态与异常

| 状态 | 含义 | 可执行操作 |
| --- | --- | --- |
| 处理中 | 正在解析、切分或生成向量。 | 查看状态；不可问答检索，不允许删除。 |
| 就绪 | 全部分块与索引可用。 | 查看分块、参与检索、删除。 |
| 失败 | 本次导入无法完成。 | 查看原因、删除；重新导入原文件作为新任务。 |

- 上传本身失败时允许不产生文档记录，界面明确提示上传失败。
- 任一分块向量化失败，整份文档不得进入“就绪”，部分结果不能参与检索。
- 服务重启时，未完成的处理任务标记为失败，并提示重新导入，不长期停留在处理中。
- 第一版没有独立的“重试处理”按钮，失败后删除记录再上传即可。
- 刷新文档管理端后重新加载文档列表与处理状态，不重复提交导入任务。
- MySQL 与 Chroma 不按单库事务处理：仅在二者写入成功后将文档设为就绪。失败时记录失败并清理本次残留索引；即使清理暂时失败，问答也必须按 MySQL 状态过滤，不得检索到半成品。
- 删除先使文档不可检索，再清理 Chroma 与 MySQL 数据。跨库删除失败时保留可重试的管理记录、继续排除检索，并提示删除失败；不能留下向用户不可见、却仍能被检索的孤立数据。

### 7.6 技术栈与最小部署边界

| 部分 | 技术选择 | 责任边界 |
| --- | --- | --- |
| 问答前端 | Vue | 独立工程，负责提问、回答与来源展示，不含文档上传和管理操作。 |
| 文档管理前端 | Vue | 独立工程，负责上传、状态、分块查看与删除，不嵌入问答业务。 |
| 业务后端 | Java | 一个服务承载两类 API 和导入处理，不拆为两个业务后端。 |
| RAG 编排 | LangChain4j | 接入生成模型与向量模型，组织分块、向量检索和有依据的回答；文档状态和持久化一致性仍由后端负责。 |
| 关系型数据库 | MySQL | 保存文档元数据、状态、分块原文和来源信息。 |
| 向量数据库 | Chroma | 独立服务保存与查询分块向量，供 Java 后端访问。 |

**最小依赖约束：**

1. LangChain4j 不是模型服务本身，仍需配置生成模型和向量模型。本版通过 Java 后端统一调用向量模型，向 Chroma 写入生成好的向量，不再额外搭建 Python RAG 服务。
2. 同一 Chroma collection 的导入和问题向量必须使用一致的向量模型配置与维度；模型或维度改变时不能直接混用旧索引。本版不提供在线切换和自动迁移功能。
3. 实施时固定 Vue、JDK、LangChain4j、MySQL、Chroma 的实际版本，并验证所选 LangChain4j Chroma 集成与 Chroma 服务端 API 的兼容性。不以两个组件“都选最新版”作为兼容保证。
4. 选定版本前，先以真实服务验证“写入向量 → 检索 → 按稳定标识删除”链路；未通过前不将兼容性写成已验证事实。
5. 最小本地运行单元是两个前端、一个 Java 后端、MySQL 和 Chroma；模型服务是必要配置依赖。是否用容器启动数据库和应用，在实施方案中确定，不额外引入 Redis、消息队列或网关。

具体版本、Java HTTP 框架、Vue 构建工具与 UI 组件库尚未确定；这些属于实施方案的选型，不改变已明确的核心技术栈。

**兼容性核查来源（2026-10-20）：** 已查阅 LangChain4j 官方 Chroma 集成文档及 Chroma 官方服务端运行文档；前者区分 Chroma REST API 版本并提供相应配置说明，后者说明独立服务及数据目录的运行方式。此次仅核查文档，没有启动服务或验证具体版本组合。

- LangChain4j Chroma 集成：`https://docs.langchain4j.dev/integrations/embedding-stores/chroma/`
- Chroma 客户端／服务端模式：`https://docs.trychroma.com/guides/deploy/client-server-mode`


## 8. 业务规则

### 8.1 文档导入与分块

| 编号 | 规则 |
| --- | --- |
| R-001 | 每次上传 1 个文件，允许 `.txt`、`.md`、`.pdf`，单文件不超过 20 MiB；前后端均校验，服务端校验为准。 |
| R-002 | TXT、Markdown 按 UTF-8 文本处理；PDF 只提取文本层，不处理扫描图片，也不承诺恢复复杂表格或多栏阅读顺序。无法获得有效文本时导入失败，给出原因。 |
| R-003 | 自动切分必须保留顺序和来源。建议默认每块最多 800 个 Unicode 字符，相邻块重叠 100 个字符；末块允许不足 800 个字符，空白块不入库，重叠不能导致切分不前进。参数仅在服务端配置。 |
| R-004 | 分块详情展示与实际索引一致的全文，不让展示文本与检索文本分别使用两套切分结果。PDF 分块记录其涉及的页码范围，不伪造无法确定的页码。 |
| R-005 | 第一版不做内容去重；同名或相同内容再次上传视为独立文档，以唯一标识区分。 |
| R-006 | 导入以整份文档为可用单位，所有必要分块处理成功后才能标记为就绪。 |

20 MiB、800 字符和 100 字符是设计初始值，不是已验证的模型最佳参数。实现保留 800 / 100 的代码缺省值；本机 BGE 模型输入上限为 512 tokens，实际配置采用 300 / 50 个 Unicode 码点。该配置已完成真实导入验证，不代表任意文本都一定低于模型上限；超限时明确报错，不静默漏掉内容。

### 8.2 问答与溯源

| 编号 | 规则 |
| --- | --- |
| R-007 | 仅检索“就绪”文档。问题去除首尾空白后不得为空，最多 2,000 个 Unicode 字符；服务端执行校验。 |
| R-008 | 使用 Chroma 向量相似度检索，候选分块默认最多 5 个，可在服务端配置；按 MySQL 的文档状态与分块记录排除无效候选，再组织上下文。只把实际选入模型上下文的分块用于本条回答的来源核对。 |
| R-009 | 空知识库或没有满足检索条件的分块时，不调用生成模型，提示“当前知识库中未找到相关依据”。检索阈值与所用模型有关，不在需求阶段指定通用分数。 |
| R-010 | 给生成模型的指令要求仅依据提供的文档内容回答。证据不足时说明不足，不用模型常识或联网信息补齐；部分问题有依据时只回答有依据的部分。 |
| R-011 | 有知识库依据的回答展示来源编号，编号必须映射到真实送入模型的分块。服务端校验来源标识，不能将模型编造的文件名或编号直接显示为已验证来源。无法核验来源时提示生成失败，不作为有效回答展示。 |
| R-012 | 点击来源可查看本次使用的原文快照；不能把全部候选分块自动当作回答已引用的证据。不要求 PDF 原文高亮或文档阅读器。 |
| R-013 | 每次问题独立检索与回答，不将前几轮消息作为推理上下文。请求进行中禁用重复发送；失败时保留问题，允许用户重新发送。 |
| R-014 | 超时、网络异常、配置缺失或模型服务失败必须与“没有相关依据”区分，不得把技术故障包装成知识库没有答案。 |

“来源真实”不等于“回答必然正确”。第一版需通过已知答案和无答案的问题验证回答行为，不承诺彻底消除模型幻觉。实现时还应校验上下文长度，超过模型限制时明确处理，不静默截断后继续宣称引用了被丢弃的分块。

### 8.3 删除、数据与安全

| 编号 | 规则 |
| --- | --- |
| R-015 | 删除成功后，文档记录、分块和向量索引均被移除；删除提交后新发起的问答不得再检索到该文档。若后台仍有残留索引，也必须先将文档排除出可检索范围；界面不能在删除未完成时提示成功。 |
| R-016 | 已发起的问答允许使用其发起时获取的资料；既有回答与来源快照不追溯修改，查看时提示其为回答时的资料，不保证文档当前仍在库中。 |
| R-017 | 文件和分块视为不可信数据，不能执行其中的脚本、HTML 或指令。文件名不能直接作为服务端存储路径；展示分块和模型输出时转义或安全渲染。模型提示中明确文档内容不是系统指令。 |
| R-018 | API Key 等凭据只保存在服务端配置，不写入前端、代码仓库或常规日志；提供不含真实凭据的配置示例。 |
| R-019 | 不提供登录只适用于本机使用；两个前端、后端及数据库服务对宿主机暴露的地址默认仅限回环地址，容器间通信不对公网开放。两个前端独立部署不构成权限隔离，不能直接作为公网或多人使用方案。 |
| R-020 | 若采用外部模型，生成分块向量会发送文档分块，生成问题向量会发送问题，生成回答会发送问题及选中的分块。运行说明必须披露数据去向；涉及敏感文档时，应先确认模型服务及数据使用许可。 |

## 9. 测试边界与策略

验收围绕真实页面、真实持久化和实际模型调用完成，不以全链路模拟结果代替。

准备一组小型测试材料：

- 一份 UTF-8 文本文档，包含“项目代号青禾，负责人林溪，上线日期为 2026 年 11 月 5 日”等可精确核对的信息。
- 一份 Markdown 文档和一份具有文本层的多页 PDF，验证格式与来源页码。
- 一份扫描型 PDF、空文件、不支持的文件和超过大小限制的文件，验证拒绝行为。
- 一个不在任何测试文档中的问题，例如询问未记载的预算金额。

测试同时观察页面结果、持久化状态、实际检索分块与模型上下文；日志核查不得泄露真实业务文档或密钥。

新项目没有旧版本兼容、数据迁移或角色权限回归范围；公网安全、多用户并发和模型效果基准不属于本次验收。
